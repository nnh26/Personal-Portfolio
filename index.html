Building next

I want to work on backend systems, not just websites. Here's my plan, in order: grow my Docs app into a full story about performance, database depth, shipping to the cloud, and messaging.

  1. Make Docs production-grade

    Next up

    Start with real sign-in and row-level security policies. Then add Redis caching, cursor-based pagination, rate limiting, request IDs, and structured logs, and load test it with k6.

    Goal: a real number to report, requests per second at a measured p95 latency.

  2. Postgres deep-dive

    Planned

    Seed a million rows, find a slow query with EXPLAIN ANALYZE, add the right index, and publish the before and after. Add PgBouncer for connection pooling.

    Goal: a write-up with query plans and timings.

  3. Ship it like a company would

    Planned

    Docker Compose for local development, GitHub Actions running tests on every push, Terraform to deploy on AWS, and dashboards with OpenTelemetry.

    Goal: infrastructure as code anyone can read, and a deploy that runs without me.

  4. Add a message queue

    Planned

    Move slow work like PDF export and email off the request path: a worker on a queue with retries and backoff, idempotency keys, and a dead-letter queue. Then publish document events through Redis Streams or Kafka, using the outbox pattern so no event is lost.

    Goal: requests stay fast while jobs run in the background, and a failed job never runs twice or disappears.

After that

  • Auth service: refresh tokens, OAuth, role-based access, OWASP tests.
  • A Go service: rewrite one piece and benchmark it against the original.
  • RAG: question answering over documents, with embeddings in Postgres.

Learning now

AWS first, then GCP. Docker, Kubernetes, Terraform, and CI/CD pipelines.
